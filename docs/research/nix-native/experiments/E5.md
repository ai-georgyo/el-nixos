# E5: `user-defined-trusted-dirs` into glibc's make, through rpmbuild

Design §9 E5 / §4.2 / §4.5 / WP0d.  Question: does a `user-defined-trusted-dirs`
value in the environment reach glibc's make when the *unmodified* glibc.spec
is built by rpmbuild, so that ld.so (64- and 32-bit) gets
`$libgccForGlibc/lib64:$libgccForGlibc/lib` as system/trusted dirs (needed
for `pthread_cancel`/`backtrace`, which dlopen `libgcc_s.so.1` by soname)?
Fallback in the design: a `configparms` line via the prep hook.

Date 2026-10-18, agent `glibc` (branch `nn/glibc`).  Scratch:
`/run/host/home/ai-shammas/.cache/el-nixos-work/glibc/e5/` (the `.nix` files
are reproduced below; they evaluate the worktree flake with `--impure`).
All builds with `nix build -L --cores 6 --max-jobs 2`.

## How glibc consumes it

`elf/Makefile` (Rocky's tree after `%prep`):

```make
$(objpfx)trusted-dirs.st: Makefile $(..)Makeconfig
	echo "$(subst :, ,$(default-rpath) $(user-defined-trusted-dirs))"    \
	| $(AWK) -f gen-trusted-dirs.awk > ${@:st=T};
```

Nothing in `Makeconfig`/`Makefile`s assigns `user-defined-trusted-dirs`, so
GNU make takes it from the environment (and exports it to every sub-make), or
from `configparms` (`Makeconfig` includes `$(..)configparms` and
`$(common-objpfx)configparms`).  glibc.spec builds with
`env LDFLAGS.so=… LDFLAGS-rtld=… %make_build -r …` inside a `build()` shell
function of `%build`; it never clears the environment.  The name is not a
shell identifier, so it can only travel as an inherited environment entry
(bash passes such entries through unchanged; it cannot assign them).

## Part 2: the Nix side of the chain (derivation → builder → bwrap → sh → make)

`link.nix`: a derivation attribute `"user-defined-trusted-dirs"` (plain, not
structured attrs), builder bash → `bwrap --bind / /` (no `--clearenv`, as the
tool shim §5.4) → `sh -c 'env LDFLAGS.so=x make -r'` → sub-make:

```
make sees: [/nix/store/x-libgcc/lib64:/nix/store/x-libgcc/lib]
sub-make sees: [/nix/store/x-libgcc/lib64:/nix/store/x-libgcc/lib]
```

`link-structured.nix`: the same with `__structuredAttrs = true` and
`env."user-defined-trusted-dirs" = …` (the form mkRpmPackage §11.1 uses)
**fails before the build starts**:

```
structuredAttrs is enabled
…-stdenv-linux/setup: line 582: declare: `user-defined-trusted-dirs=/nix/store/x-libgcc/lib64:/nix/store/x-libgcc/lib': not a valid identifier
```

nixpkgs' setup.sh exports structured `env` entries with
`declare -x "${envVar}=…"`, which rejects non-identifiers (nixpkgs' own glibc
passes it as a `makeFlags` entry instead).  So §8.1's "hyphenated make vars via
`env`" cannot be implemented by copying the override's `env` into the
derivation's `env`.

## Verdict: the working mechanism

1. **Environment, set on rpmbuild's command line.**  Verified end-to-end with
   the unmodified spec (parts 1, 4).  `packages/glibc/default.nix` keeps the
   value in `env."user-defined-trusted-dirs"` (§8.1/§11.5 field), but
   **mkRpmPackage (WP6) must not put names that are not shell identifiers into
   the derivation's structured `env`** (part 2: stdenv aborts).  It should pass
   them as `env 'NAME=VALUE' … rpmbuild` (or `bwrap --setenv NAME VALUE`) in
   the build phase, e.g. from a separate structured attribute
   (`rockyMakeEnv`) that bash reads as an associative array, where hyphenated
   keys are fine.  Valid identifiers (`NIX_NO_SELF_RPATH`, `NIX_DONT_SET_RPATH`)
   stay in the derivation `env`.
2. **Fallback, equivalent result:** `prepScript = "echo 'user-defined-trusted-dirs=…' > configparms"`
   (source dir, run by the prep hook after `%prep`; part 3).  Needs no WP6
   support beyond `prepScript`, but it is glibc-specific and overrides any
   environment value.
3. The value references `libgccForGlibc` (which references nothing), so the
   relocated glibc's `out` gets exactly one foreign reference: the named S1
   exception of §0.4.1.
